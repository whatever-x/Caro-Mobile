# 학습 브랜치 디자인 토큰 정합성 감사 설계

## 목표

`develop`부터 현재 작업트리까지 이 브랜치에서 변경된 Compose UI의 색상, 타이포그래피, 간격, 크기, 모양을 Figma 원본과 대조한다. Figma 변수와 프로젝트 디자인시스템의 대응 관계를 확인하고, 불일치를 수정해 구현 결과가 Figma와 동일한 시각 값을 사용하도록 한다.

## 감사 범위

- 기준 diff는 `develop...HEAD`의 커밋 변경과 현재 작업트리의 미커밋 변경을 합친 범위다.
- `feature/learning`의 학습 화면, 중단 다이얼로그, 완료 화면과 관련 컴포넌트를 모두 확인한다.
- 학습 진입을 위해 변경된 `feature/home`, `feature/deck-detail`의 Compose UI 변경 라인도 확인한다.
- 상태, 저장 정책, 네비게이션 및 카드 평가 동작은 변경하지 않는다.
- 기존 파일의 브랜치 변경과 무관한 UI는 감사 범위에서 제외한다.

## Figma 대조 방법

- 제공된 Caro Design 파일의 일일학습 및 전체학습 화면 노드를 기준으로 삼는다.
- 각 변경 UI에서 사용하는 Figma 변수 이름과 해석된 실제 값을 모두 수집한다.
- 색상, 타이포그래피, 간격, 모양, 고정 크기별로 코드 값을 대응시킨다.
- 이름이 비슷하다는 이유만으로 동일 토큰으로 판단하지 않고 의미와 실제 값이 모두 일치하는지 확인한다.
- Figma에 변수 바인딩이 없는 수치는 해당 노드의 렌더링 값과 레이아웃 메타데이터를 기준으로 확인한다.

## 토큰 적용 우선순위

1. Figma 토큰과 동일한 의미 및 값을 가진 프로젝트 토큰이 있으면 기존 `CaroTheme` 토큰을 사용한다.
2. Figma에는 토큰이 있지만 프로젝트에는 대응 토큰이 없으면 `core:designsystem`에 동일한 의미와 값의 전역 토큰을 추가하고 feature에서 이를 사용한다.
3. Figma에도 토큰이 없는 값만 사용하는 화면 파일에 의미 있는 이름의 `private val` 하드코딩 리소스로 선언한다.
4. Figma와 프로젝트에 같은 의미의 토큰이 있지만 값이 다르면 기존 사용처의 영향 범위를 확인한다. 공용 토큰 수정이 다른 화면을 깨뜨릴 가능성이 있으면 Figma 의미에 맞는 별도 토큰을 추가한다.
5. Preview 전용 크기와 테스트 데이터는 실제 제품 UI 토큰 감사에서 제외한다.

## 코드 구조

- 전역 토큰은 기존 `CaroColor`, `CaroTypography`, `CaroSpacing`, `CaroShape` 구조와 foundation defaults 패턴을 따른다.
- Figma 비토큰 값의 로컬 리소스는 사용 범위에 따라 해당 Screen 또는 component 파일의 최상위 `private val`로 둔다.
- 사용자 노출 문자열은 계속 Compose resources를 사용한다.
- 토큰 정비를 이유로 컴포넌트 API, MVI 상태 또는 학습 모드 분기 구조를 바꾸지 않는다.

## 검증

- 변경 전후 토큰 매핑표를 작성해 Figma 변수, Figma 실제 값, 프로젝트 토큰 또는 로컬 리소스를 추적한다.
- 관련 feature 테스트를 실행한다.
- 변경된 모듈의 Spotless 검사와 `git diff --check`를 실행한다.
- 프로젝트 전체 Spotless가 범위 밖 기존 변경 때문에 실패하면 해당 파일과 실패 원인을 별도로 기록한다.
- 일일학습과 전체학습 중단 다이얼로그 Preview를 포함해 조건부 행의 유무와 여백을 확인한다.

## 완료 조건

- 감사 범위의 실제 제품 UI에 설명 없는 매직 색상, 타이포그래피, 간격, 크기 또는 모양 값이 남아 있지 않는다.
- 모든 값이 Figma 토큰 기반 프로젝트 토큰 또는 Figma 비토큰 기반 로컬 하드코딩 리소스로 분류된다.
- Figma와 다른 프로젝트 토큰 사용이 남아 있지 않는다.
- 기능 테스트와 변경 모듈 포맷 검사가 통과한다.
